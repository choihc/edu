Part 1 · AI 시대의 코딩
Why

AI가 다 짜준다는데, 왜 굳이 코딩을 알아야 할까요?

대화창에 붙어 있는 사람과, 그것을 응용하는 사람의 격차는 점점 벌어집니다.
  • 요구사항을 데이터 구조로 번역할 수 있어야 AI에게 정확히 지시할 수 있습니다.
  • AI 결과가 맞는지·잘못됐는지 판단하려면 코드 동작 감각이 필요합니다.
  • 대화창 밖으로 나와 API·자동화·워크플로우로 연결해야 진짜 생산성이 시작됩니다.
  • AI는 "맥락"을 먹고 자랍니다. 좋은 맥락은 코드와 데이터를 다룰 줄 아는 사람이 만듭니다.
"코딩을 모르는 사람은 AI에게 일을 시키는 것이 아니라, AI에게 휘둘립니다."

Logic

조건문과 반복문 — "만약에"와 "여러 번"

코드는 결국 판단하고 반복합니다. 이 두 개만 알아도 절반은 이해한 셈입니다.

if / else — 조건에 따라 갈래길

// 회원이면 10% 할인, 아니면 정가
if (customer.isMember) {
  finalPrice = price * 0.9;
} else {
  finalPrice = price;
}
실생활: "회원입니까?" → 두 갈래 중 한쪽으로 흘러가는 카페 카운터

for — 같은 일을 여러 번

// 100건 주문을 한 번에 처리
for (const order of orders) {
  sendReceipt(order);
  saveToDB(order);
}
실생활: 컨베이어 벨트에서 박스가 하나씩 같은 작업을 거치는 모습

Part 1 · 디버깅 마인드셋
Debugging

에러는 적이 아니라 길잡이입니다

코드는 항상 깨집니다. 잘 짜는 사람은 "안 깨는 사람"이 아니라 "깨진 걸 빨리 고치는 사람"입니다.
1
어디서 깨졌나? — 위치 먼저
에러 메시지 맨 위 줄에 보통 파일·줄 번호가 적혀 있습니다. 그 줄부터 읽으세요. 다른 줄은 잠시 무시.
2
무엇이 잘못됐다고 말하나? — 키워드 한 줄
"undefined is not a function" / "Cannot read property of null" — 영어가 어려우면 그대로 검색하세요. 같은 에러를 만난 사람이 반드시 있습니다.
3
내 가정이 어디서 틀렸나? — 한 줄씩 확인
"여기에 값이 있을 거라 가정했는데 없었구나." 디버깅의 90%는 자기 가정과 실제의 차이를 찾는 일입니다.
🤖
AI에게 디버깅 시키기 — 에러 메시지 + 관련 코드 + "내가 기대한 동작은 X였는데 실제로는 Y"를 던지면, 대부분 한 번에 원인을 찾아줍니다.

사람의 말은 모호합니다. 시스템 사이를 오갈 데이터는 정확한 모양이 필요합니다 — 그게 JSON입니다.

🗣 사람의 말 (자연어)

Part 1 · API와 HTTP
Web

API는 서비스끼리 주고받는 약속된 대화입니다

웹 위의 모든 것은 결국 — "내가 이렇게 부탁했더니, 이렇게 답을 줬다."

HTTP 메서드 — "어떤 부탁인가"

GET
읽기 — "데이터 좀 줘"
POST
생성 — "이거 새로 만들어줘"
PUT
수정 — "이걸로 바꿔줘"
DELETE
삭제 — "이거 지워줘"

상태 코드 — "어떻게 답했나"

2xx · 잘 됐어요 (200 OK)
4xx · 너의 잘못이야 (404 없음, 401 권한)
5xx · 서버 잘못이야 (500 에러)
🤖
Claude·GPT API도 같은 모양 — POST 요청에 프롬프트(JSON)를 담아 보내면, 모델이 답(JSON)을 돌려줍니다. 즉, AI는 "특별한 무언가"가 아니라 JSON을 잘 다루는 또 하나의 서버일 뿐입니다.

Part 2 · 왜 "엔지니어링"인가 (1/2)
Why · 품질

AI를 잘 쓰는 것은 기술이 아니라 설계의 문제입니다

먼저, 결과의 품질을 떠받치는 3개의 축부터 살펴봅니다.
🎯

일관성 (Consistency)

같은 입력에 같은 품질의 답을 받으려면 구조가 필요합니다. "운"으로 잘 나오는 답은 서비스가 될 수 없습니다.

🔁

반복성 (Reproducibility)

한 번 잘 나온 답을 100번, 1000번 재현하려면 프롬프트·도구·검증을 시스템으로 묶어야 합니다.

🛡️

안전성 (Safety)

Zero-shot

패턴 ① Zero-shot — 예시 없이 바로 부탁

가장 단순한 형태. 모델이 이미 잘 아는 일반적인 작업에 적합합니다.
🎯
Zero-shot

예시 한 개도 없이 — 그냥 부탁

모델이 사전 학습으로 이미 알고 있는 영역의 일이라면, 굳이 예시를 줄 필요가 없습니다. 가장 빠르고 가벼운 방법이지만, 모호한 작업에는 결과가 흔들립니다.
👍 이럴 때 좋아요
번역 · 요약 · 일반 상식 질문 · 잘 정의된 글쓰기
⚠️ 한계
회사 내부 규칙·도메인 특수 작업에서는 일관성이 떨어집니다
▼ PROMPT
다음 영어 문장을 한국어로 자연스럽게 번역해줘. "The quick brown fox jumps over the lazy dog."
▶ OUTPUT
빠른 갈색 여우가 게으른 개를 뛰어넘는다. → 예시 없이도 정확히 번역됩니다. 모델이 이미 번역을 잘 알고 있기 때문.

Few-shot

패턴 ② Few-shot — 예시 2~5개로 가르치기

"이런 식으로 답해줘"의 모범답안 몇 개만 보여줘도, 출력 일관성이 극적으로 올라갑니다.
📚
Few-shot

"예: A → X" 패턴 몇 개를 보여준다

모델은 예시에서 "이 작업의 규칙"을 추론합니다. 카테고리·포맷·말투를 일관되게 만드는 가장 강력한 방법.
👍 이럴 때 좋아요
분류 · 출력 포맷 통일 · 사내 양식 변환 · 회사 톤 유지
📈 효과
분류 정확도 60% → 90%+로 점프하는 경우가 흔합니다
▼ PROMPT
고객 문의를 카테고리로 분류해줘. 예시: Q: "결제가 안 돼요" → 결제 Q: "비밀번호 까먹었어요" → 계정 Q: "배송이 늦어요" → 배송 지금 분류할 문의: "카드 등록이 자꾸 실패해요"
▶ OUTPUT
결제 → 예시 3개만으로 모델은 "카테고리는 한 단어, 결제 관련 키워드는 결제로"라는 규칙을 학습합니다.

Chain-of-Thought

패턴 ③ Chain-of-Thought — 단계별로 생각하게 시키기

"단계별로 풀고 답해줘" 한 마디만 추가해도 — 추론·계산 정확도가 크게 올라갑니다.
🧮
CoT

곧바로 답하지 말고 — 풀이 과정을 적어라

사람도 암산보다 풀이를 적으면서 풀 때 정확합니다. 모델도 마찬가지. 단계별 사고를 강제하면 중간 실수가 줄어듭니다.
👍 이럴 때 좋아요
계산 · 다단계 추론 · 의사결정 · 코드 디버깅 · 문제 해결
📈 효과
수학·논리 문제에서 정확도 +30~40%p (Anthropic·Google 연구)
▼ PROMPT
사과 3개에 1,500원이고, 배 2개에 4,000원이다. 사과 5개와 배 3개를 사면 총 얼마인가? 단계별로 풀이를 적은 뒤 마지막 줄에 정답을 써줘.
▶ OUTPUT
1) 사과 1개 가격: 1,500 ÷ 3 = 500원 2) 배 1개 가격: 4,000 ÷ 2 = 2,000원 3) 사과 5개: 500 × 5 = 2,500원 4) 배 3개: 2,000 × 3 = 6,000원 5) 합계: 2,500 + 6,000 = 8,500원 답: 8,500원

Role + Context

패턴 ④ Role + Context — 역할과 상황을 깔아주기

같은 질문이라도 "누가, 어디서, 무엇을 위해"를 알려주면 — 답의 톤·깊이·실용성이 완전히 달라집니다.
🎭
Role + Context

"너는 누구다 + 우리 상황은 이렇다"

모델은 "어떤 답이 적절한가"를 컨텍스트에서 추론합니다. 역할·청중·제약을 미리 깔면, 일반 답변이 도메인 맞춤형 답변으로 바뀝니다.
👍 이럴 때 좋아요
전문 글쓰기 · 자문 · 기획서 · 톤이 중요한 응답 (CS, 영업 등)
📈 효과
"일반론" → "우리 상황에 맞는 구체적 조언"으로 결과 변화
▼ PROMPT
[역할] 너는 10년차 보안 엔지니어다. [상황] 우리는 사용자 100만명 핀테크 스타트업, 결제·계좌 데이터를 다룬다. [청중] 이번 주 입사하는 신규 개발자. 신규 개발자가 첫 주에 반드시 지켜야 할 보안 수칙 5가지를 우선순위 순으로 정리해줘.
▶ OUTPUT
1) 운영 DB 직접 접근 금지 — 결제 데이터는 PII로 분리 저장, 조회는 감사 로그 남는 도구만 사용 2) 로컬에 카드번호·CVV 저장 금지 — 디버깅 중에도 절대. 마스킹된 테스트 데이터 활용 3) 2차 인증 + 하드웨어 키 의무화 4) 코드에 비밀키 하드코딩 금지 — Vault·Secret Manager 사용 5) 이상 거래 시 즉시 #security 채널 보고 → 일반론이 아니라, 핀테크·신규 입사자에 맞춘 답변

Self-Critique

패턴 ⑤ Self-Critique — 스스로 비판하고 다시 쓰게 하기

한 번에 좋은 답이 나오지 않을 때 — 모델 자신에게 검토를 시키면 품질이 한 번 더 올라갑니다.
🔁
Self-Critique

"쓰고 → 비판하고 → 다시 써라"

하나의 프롬프트 안에 초안 작성 → 자기 비판 → 개선안 3단계를 묶습니다. 사람의 셀프 리뷰와 같은 효과를 한 번의 호출로 얻을 수 있습니다.
👍 이럴 때 좋아요
보고서 · 메일 · 코드 리뷰 · 마케팅 카피 · 품질이 결과를 가르는 산출물
📈 효과
1라운드 결과 대비 평균 +20~30% 품질 향상 (가독성·구조·설득력)
▼ PROMPT
아래 작업을 순서대로 해줘. 1단계. 거래처에 결제 일정 지연을 양해 구하는 메일 초안을 써라. 2단계. 그 초안을 직접 비판해라. (약점 3가지를 솔직하게) 3단계. 비판을 반영한 개선된 최종안을 써라.
▶ OUTPUT (요약)
초안 · "결제 지연 안내드립니다…" (형식적) 자기 비판 ① 사과가 너무 늦게 등장 ② 새 일정이 모호함 ③ 보상·CTA 누락 최종안 · "먼저 사과드립니다. 새 결제일은 11/20로 확정되었으며, 지연 보상으로…" → 한 번의 호출로 초안과 개선안을 동시에 확보

Part 2 · 컨텍스트
Context · RAG

AI에게 "무엇을 보여줄지"가 절반 이상을 결정합니다

컨텍스트 윈도우는 한정 자원 — 적절한 정보를 적시에 주입하는 설계가 곧 품질입니다.
1
RAG (Retrieval-Augmented Generation)
사내 문서·DB를 벡터로 인덱싱 → 질문이 들어오면 관련 조각만 검색해 컨텍스트에 끼워 넣음. "AI에게 회사 위키를 통째로가 아니라, 필요한 페이지만"
2
메모리 (Memory)
긴 대화·작업 흐름에서 중요한 사실을 별도 저장 → 다음 호출에 다시 주입. 예: "이 사용자는 React 베테랑이고 한국어 선호" 같은 프로필.
3
컨텍스트 압축 / 캐싱
반복되는 시스템 프롬프트·도구 정의는 프롬프트 캐싱으로 90% 비용 절감. 길어진 대화는 요약본으로 압축해서 다시 주입.
📐
"컨텍스트 엔지니어링"이라는 새 개념이 부상한 이유 — 모델이 좋아져도, 무엇을 보여줄지 잘못하면 결과가 나빠지기 때문입니다.

Part 2 · 평가(Evals)
Eval

평가가 없는 AI는 — 운에 맡긴 서비스입니다

"좋아진 것 같다"는 느낌이 아니라, 테스트로 측정해야 진짜 개선이 가능합니다. (= AI판 TDD)
🧪 TDD 관점으로 보면  ·  전통 SW에서 테스트 코드가 함수의 정답을 잡아주듯, AI에게는 평가셋(Eval Set)이 같은 역할을 합니다. "먼저 기대 출력을 적고 → 시스템을 그 기대에 맞춘다" — 순서가 곧 TDD 그 자체.
1
평가셋(Eval Set) 만들기 — = 테스트 케이스 작성
대표적인 입력 50~200개 + 정답(또는 좋은 답의 기준)을 먼저 적습니다. 코드의 단위 테스트를 먼저 짜는 것과 같습니다. 작아도 좋습니다 — 없는 것보다 1000배 낫습니다.
2
변경 시마다 회귀 테스트 — = CI 파이프라인
프롬프트·모델·도구를 바꿀 때마다 평가셋 전체 재실행. 점수가 떨어지면 배포 차단. "어제는 됐는데 오늘 안 되는" 사고를 막는 건 결국 자동화된 테스트뿐입니다.
3
자동 채점 + 사람 검수 병행 — = 단위/통합 테스트
간단한 건 LLM이 채점(LLM-as-judge), 핵심은 사람이 직접. 단위 테스트로 빠르게 회귀를 잡고, 통합 테스트로 사용자 경험을 검증하는 구조 그대로입니다.
📊
현실적 시작점 — 거창한 평가 시스템 만들기 전에, 스프레드시트에 입력 30개 + 기대 답을 적고 매주 한 번 돌리세요. 이게 곧 "AI 프로젝트의 첫 테스트 코드"입니다. 그것만으로도 운영 품질이 즉시 달라집니다.

Part 2 · 사례 연구
Case Studies

실제 회사들의 — 성공과 실패

교과서가 아닌, 시장에서 검증된 사례에서 배웁니다.
✅ 성공 사례
Cursor
"AI 코드 에디터" 카테고리 자체를 만들어냄. 모델이 아닌 하네스(에디터·도구·UX)를 잘 설계해 1년 만에 ARR $100M 달성.
Klarna
고객지원 챗봇이 700명분 업무 처리. 평균 응답시간 2분 → 즉시. 핵심은 잘 큐레이팅된 컨텍스트와 평가.
GitHub Copilot
코드 자동완성으로 개발자 생산성 +55%. "한 줄 단위 제안"이라는 좁은 문제 정의가 성공 비결.
⚠️ 교훈을 남긴 사례
Air Canada 챗봇 소송
챗봇이 잘못된 환불 정책을 안내 → 법원이 항공사 책임 인정. 가드레일·검증 없이 챗봇을 배포한 결과.
McDonald's 드라이브스루
3년 시범 후 IBM과의 AI 주문 시스템 종료. 시끄러운 환경·다국어 한계. "엣지 케이스에서 무너지면 0점".
초기 기업 챗봇들 (다수)
"GPT 한 번 호출 = 서비스" 시도. 환각·일관성 부재로 신뢰 잃고 철수. 하네스 부재가 공통 원인.

Part 2 · 운영 경제학
Cost

같은 결과를 — 10분의 1 비용으로

AI 서비스의 손익은 모델 선택이 아니라 "어떻게 쓰는가"에서 갈립니다.
🎚

모델 라우팅

쉬운 작업 = Haiku, 보통 = Sonnet, 어려운 작업 = Opus. 분기 처리만 잘해도 평균 비용이 70% 줄어듭니다.

💾

프롬프트 캐싱

반복되는 시스템 프롬프트·문서를 캐싱. 같은 컨텍스트 두 번째 호출부터 90% 비용·지연 절감.

📦

배치 처리

실시간 답이 필요 없는 작업은 Batch API로. 단가가 절반 — 야간 일괄 처리에 효율적.

✂️

컨텍스트 압축

긴 문서는 요약 후 사용. 토큰 1만 → 1천으로 줄이면 비용·속도 모두 10배 ↑.

🚦

가드레일 우선

잘못된 요청은 모델 호출 전에 차단. 비용도 아끼고 안전성도 ↑ — 정규식·간단 분류기로도 충분.

📈

지속적 측정

호출당 비용·성공률·지연을 대시보드로 보지 않으면 새는 비용을 알아챌 수 없습니다.
